# The Graph Store Runs On PostgreSQL, And Graph Reads Are Dataset Scoped

- Status: Accepted
- Date: 2026-08-03
- Relates to: [ADR-0009](0009-mesh-read-isolation-presence-vs-content.md),
  [ADR-0010](0010-structured-knowledge-durable-source-of-truth.md),
  [ADR-0015](0015-one-process-owns-the-graph.md),
  [ADR-0018](0018-corpus-totals-are-authoritative-not-uptime.md),
  [ADR-0021](0021-retrieval-interface-owns-ranking-and-provenance.md),
  [ADR-0023](0023-control-plane-outside-the-application.md). Makes ADR-0015
  revisitable without revisiting it.

Citadel's **Knowledge Index** is split across two datastores: the relational and vector halves live in PostgreSQL, and the graph half lives in an embedded, single-writer, file-locked engine on a mounted volume. That split is the reason [ADR-0015](0015-one-process-owns-the-graph.md) exists, and it is the reason a **Node** cannot be scaled past one web worker. It also makes automated per-organisation provisioning awkward, because standing up an instance means standing up a database service and a durable volume rather than one database. This ADR decides both halves of a single change: the graph store moves to cognee's PostgreSQL graph provider, and the five graph operations Citadel issues stop resolving a single default engine and instead resolve inside a per-dataset context. Upstream registers a per-dataset database handler for the PostgreSQL graph provider (`cognee/infrastructure/databases/dataset_database_handler/supported_dataset_database_handlers.py`, key `postgres_graph`), and both changes land on the same call sites, so a store move that ignored the scoping would be the same edit performed twice, with the second pass invalidating whatever the first pass was tested against. The five operations, all in `kb/cognee_client.py`, are the whole-graph read `get_graph_data()` in `_read_graph_data` (`kb/cognee_client.py:736`), the batched node-presence lookup `get_nodes` in `corpus_graph_presence` (`kb/cognee_client.py:1096`), the single-node read `get_node` and the incident-edge read `get_connections`, both in `_document_graph` (`kb/cognee_client.py:1251` and `kb/cognee_client.py:1255`), and `delete_nodes` in `delete_graph_nodes` (`kb/cognee_client.py:1189`). Every one of them reaches the store through `get_graph_engine()`. None of them sends a query string: a grep for `cypher` and `engine.query` across `kb/`, `scripts/` and `tests/` returns nothing, and every hit for `match` is a Python `re` or `fnmatch` call, an identifier containing the word, or English prose, so Citadel has no Cypher surface to port and the migration is confined to the adapter methods above.

The label in configuration is also wrong and gets fixed here. `.env.example:258` and `docs/operations.md:46` both set `GRAPH_DATABASE_PROVIDER=kuzu`, but upstream resolves that string to the maintained successor package: `cognee/infrastructure/databases/graph/kuzu/adapter.py` in the installed distribution is a shim whose docstring reads "Legacy import path for the Ladybug graph adapter", and the real class is `LadybugAdapter`. Citadel already imports it under its true name at `kb/cognee_client.py:139`. A configuration value that names a package which is not what runs costs an investigation every time someone reads it, so retiring the alias is part of this decision rather than a follow-up.

**Considered Options**

- **Keep the embedded engine and mitigate the lock:** detect a stale lock file at boot, remove it, restart the process. Cheapest by a wide margin and needs no re-cognify. It mitigates a failure class instead of removing one: upstream issue 3708, "Kuzu worker crash leaves orphaned database lock, blocking all subsequent recall() calls", names the version line Citadel pins, and the merged fix has more components than the pin carries (read from the upstream issue against the installed source on 2026-08-03; the issue is not a file in this repository and the reading is not reproducible from it). The PostgreSQL adapter holds an in-process `asyncio.Lock` for writes and takes no OS file lock, so the orphaned-lock failure mode has nowhere to live. Recovery logic that has to guess whether a lock is orphaned or held is exactly the kind of code that ships inert and is only discovered during an incident.
- **Move the store now, scope the reads later:** a smaller first change with a smaller blast radius, and tempting for that reason. Rejected on cost. All five operations get rewritten in pass one and rewritten again in pass two, and the search result shape changes in pass two, after every caller has been re-verified against pass one. Two migrations, two re-cognify decisions, one benefit.
- **Turn on per-dataset context without moving the store:** upstream registers `LadybugDatasetDatabaseHandler` under both `ladybug` and `kuzu`, so partitioning is reachable on the current backend. Rejected because a per-dataset embedded graph is a per-dataset file lock, which multiplies the failure this decision exists to remove rather than removing it.
- **Neo4j or Memgraph as a graph server:** a genuine option, with a first-class upstream dataset handler already present for Neo4j. It delivers concurrent openers and per-dataset partitioning. It also adds a second datastore to provision, licence, back up, upgrade and monitor for every organisation instance, which is the operational cost [ADR-0023](0023-control-plane-outside-the-application.md) is trying to keep bounded. One PostgreSQL per instance is the shape that makes automated provisioning tractable.
- **The remote server mode of the embedded engine:** [ADR-0015](0015-one-process-owns-the-graph.md) names this as the thing that would reverse it, and it is the smallest conceptual jump. It still introduces a second service into the deployment, and it leaves the per-dataset read unbuilt, so the scoping work would have to be planned against a different backend afterwards.
- **A Redis-backed shared lock across processes:** upstream's only supported cross-process sharing mode for the embedded engine. [ADR-0015](0015-one-process-owns-the-graph.md) already rejected it: an extra infrastructure dependency, and every query pays an open and close of the database on the interactive search path.

**Consequences**

- The org-wide graph read becomes a loop. `graph_data()` currently issues one `get_graph_data()` against one engine; under per-dataset context it issues one per dataset and merges, with node-id deduplication because a document reachable from two datasets returns twice. Cost goes from one query to O(datasets). The existing TTL cache and single-flight lock in `CogneePublicClient.graph_data` (`kb/cognee_client.py:701`) become load-bearing rather than an optimisation, since they now amortise N queries instead of one.
- Under per-dataset context, `_backwards_compatible_search_results` in `cognee/modules/search/methods/search.py` returns one entry per dataset carrying `dataset_id`, `dataset_name` and `dataset_tenant_id` alongside the results. `CogneePublicClient.recall` returns a flat list, so every caller that parses search results has to migrate. `kb/search_format.py`, the `/search` envelope, and the seed-query enumeration in `kb/promotion.py` all read that shape. Promotion issues no graph reads of its own (it enumerates a **Seat** dataset through semantic recall and writes back through the ingest path), so it is untouched by the store move and touched by the shape change. The shape change is absorbed by the adapter [ADR-0021](0021-retrieval-interface-owns-ranking-and-provenance.md) introduces: with that interface in place the new result shape stops at the adapter, and these callers migrate once rather than twice.
- `DATABASE_MAX_LRU_CACHE_SIZE` has to be raised before this ships. It caps the `closing_lru_cache` around cognee's graph and vector engine factories (`get_graph_engine.py:244`, `create_vector_engine.py:153`) and the plain `lru_cache` around the relational one (`create_relational_engine.py:9`), and the installed default is 6 (`cognee/shared/lru_cache.py:10`). With more datasets than that, an org-wide read evicts and reopens engines as it walks the loop, tearing down and rebuilding a connection pool per dataset per read. The variable must be set before cognee is imported, so it belongs in the deployment environment.
- Creating a per-dataset database at runtime requires the `CREATEDB` privilege on the application role. Verify that against the managed PostgreSQL the node runs on before any other work in this project. If the privilege is unavailable, the scoped-read half is blocked and the store move has to ship on its own, which is the sequencing this ADR otherwise rejects.
- The data side is a full re-cognify, not a migration. There is no export path from the embedded graph into the PostgreSQL adapter, and the graph is a rebuildable projection of **Structured Knowledge** by [ADR-0010](0010-structured-knowledge-durable-source-of-truth.md), so rebuilding it is the supported operation. Plan it as one job with the existing re-index backlog, because re-cognifying documents that were accepted and never indexed is the same operation on a different set of rows.
- The **Knowledge Mesh** empty-graph fallback needs a new definition of empty. `kb/knowledge_mesh.py` returns `fallback_graph("graph_empty", presence)` when the single read comes back with no nodes. Under a loop, one dataset failing must not present as an empty vault, and one dataset being genuinely empty must not suppress the rest. **Seat Presence** hubs keep rendering either way, per [ADR-0009](0009-mesh-read-isolation-presence-vs-content.md).
- Relational reads are unaffected. `node_dataset_map`, `document_counts_by_dataset`, `corpus_page`, `corpus_totals` and `corpus_chunk_counts` read the relational and vector stores through SQLAlchemy sessions and never open the graph, so the dataset attribution [ADR-0009](0009-mesh-read-isolation-presence-vs-content.md) depends on and the census [ADR-0018](0018-corpus-totals-are-authoritative-not-uptime.md) rests on both survive this change untouched. Only `corpus_graph_presence` crosses over, because it asks the graph a question.
- `GRAPH_DATABASE_PROVIDER=kuzu` is retired from `.env.example`, `docs/operations.md` and `tasks.md:776`, and the `/data` volume stops being where the graph lives. Whether the volume is still needed for anything else is a separate question that this project has to answer before the volume is removed.
- This decision is executed by the [graph store migration runbook](../superpowers/specs/2026-08-04-graph-store-migration-runbook.md), which turns it into nine gates. The first is the privilege check named above, because a negative answer changes the shape of the whole plan rather than one step of it.
- [ADR-0015](0015-one-process-owns-the-graph.md) becomes revisitable. Its "what would reverse this" section names a backend supporting concurrent openers, and this is one. Revisiting it is not part of this decision: moving the **Learning Process** back out of the web loop and running a second uvicorn worker are separate changes with their own verification, and neither should ride the migration that merely makes them possible.
