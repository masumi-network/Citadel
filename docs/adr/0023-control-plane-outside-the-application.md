# One Organization, One Instance: The Control Plane Lives Outside The Application

Citadel deploys today as one **Organization Vault** for one organisation. `railway.toml` gives every service the same entry command, `python -m scripts.run_railway`, with `CITADEL_RUN_MODE` selecting the role (`web` by default, plus `pipeline`, `learning-agent`, `linear-sync`, `backup-mirror`, per `docs/operations.md:25-29`); `docs/operations.md:23-56` then describes the shape around it, a Postgres with `pgvector` enabled, a volume mounted at `/data` holding the graph store and the access store, `SYSTEM_ROOT_DIRECTORY` and `DATA_ROOT_DIRECTORY` pointing into that volume, and a `DATABASE_URL` from which Citadel derives cognee's split `DB_*` settings. The rest of a deployment is flat environment configuration: default and search-default dataset (`docs/operations.md:126-130`), the model provider binding (`:137-142`), and generated bootstrap access keys plus the access store path (`:158-166`). Selling that to a second organisation forces a decision about where separation between organisations lives, and the two available answers are not equally provable: a query predicate that scopes rows by organisation is only as good as the least careful call site and cannot be believed without a code audit, while a deployment boundary is a thing a buyer's counsel can inspect directly. So **each organisation gets its own dedicated deployment with its own database, and organisation signup provisions one automatically.** The system that owns signup, provisioning, instance lifecycle (create, upgrade, suspend, delete, export), domain assignment, secret management, billing, and fleet telemetry is a separate system from Citadel, and Citadel must never learn that other instances exist. That last clause carries the weight, and it is why the boundary is architectural rather than organisational: separation between organisations is a property of the deployment only for as long as the application has no fleet awareness, and the moment it gains any, the property is gone and the claim is once again a claim about code. The scope of this decision is separation *between* organisations. Separation between **Seats** inside one organisation is governed by [ADR-0003](0003-seat-node-central-private-memory.md) and [ADR-0009](0009-mesh-read-isolation-presence-vs-content.md), and nothing here changes it.

**Considered Options**

- **Multi-tenant with in-code scoping:** one deployment, one database, an organisation key on every row and every query. It has the lowest cost per organisation by a wide margin and the least infrastructure to operate. It loses because it converts every read path in the system into a security-critical path, permanently: search, the **Knowledge Index**, the **Knowledge Mesh** surfaces, activity, dashboards, exports, and every future surface would each have to carry the predicate and keep carrying it. The guarantee it produces is exactly the kind that needs an audit before a buyer should accept it, and small buyers do not commission audits.
- **Namespace per organisation on a shared cluster:** one runtime substrate, per-organisation namespaces, schemas, or databases inside it. Cheaper than a full instance and operationally familiar. It loses on the same ground one layer down: anything genuinely shared (a process, a connection pool, a graph engine) makes the separation a property of configuration again, and [ADR-0015](0015-one-process-owns-the-graph.md) already establishes that the graph is owned by exactly one process, so process-level co-tenancy is not something the current architecture offers for free.
- **A dedicated instance per organisation, provisioned by hand:** the isolation this decision wants, available today with no new system to build, and it is how the first few deployments will actually happen. It does not survive signup. Each instance needs a database with the extension enabled, a volume, a domain, a generated set of access keys, a model provider binding, and a set of dataset defaults, and hand-built infrastructure drifts between instances until no two are the same and no upgrade is safe. Correct as a starting posture, insufficient as the decision.
- **A dedicated instance per organisation, provisioned automatically by a control plane (chosen):** the same isolation, with the per-organisation setup expressed once as code that a signup can execute. It buys a separation story that survives procurement, an upgrade path that can be reasoned about because instances are identical by construction, and a clean place to put billing and lifecycle. It costs a second system to build and operate, and that system holds credentials for every instance, which makes it the most sensitive component in the product.
- **Accepting the per-organisation cost floor:** stated plainly because it is the real objection. Per-instance isolation means a fixed floor of compute and storage per organisation regardless of usage: a web process, a database, a volume, and whatever inference topology is chosen, all running for an organisation that ingests nothing that month. That floor sets the minimum viable price and rules out a free hosted tier. It is accepted rather than solved, because every way of removing the floor removes the deployment boundary that the model exists to provide.

**Consequences**

- Fleet upgrades become the hardest ongoing operational problem in the product, and the strategy has to exist before the fleet does. One instance is a deploy. Two hundred instances is a migration campaign against two hundred independent data states, where a failure mode that is rare per instance is certain somewhere in the fleet on every rollout. Version skew across instances becomes normal and has to be a supported condition rather than an incident.
- Unattended dependency movement changes severity with fleet size. `requirements.txt:1-6` pins cognee to the 1.2.x line and records why: [ADR-0009](0009-mesh-read-isolation-presence-vs-content.md) dataset attribution reads private cognee internals that a 1.3.x could move, which would fail closed and blank a scoped caller's vault, and the pin exists so a Railway build cannot pull one unattended. At one instance that is a support ticket. Across a fleet it is a simultaneous incident with no single rollback. This is an argument for the interface in [ADR-0021](0021-retrieval-interface-owns-ranking-and-provenance.md) that is independent of ranking and provenance: a pinned engine behind a contract Citadel owns is upgradable one instance at a time, while a pinned engine called directly from many call sites is not.
- The provisioner's unit of work is a versioned artifact, not a runbook. Per organisation it creates a web service running the existing entry command, a Postgres with `CREATE EXTENSION IF NOT EXISTS vector` applied before first ingest, a `/data` volume with `SYSTEM_ROOT_DIRECTORY` and `DATA_ROOT_DIRECTORY` under it, the graph provider setting, the dataset defaults, freshly generated access keys with the access store path, a model provider binding, and a domain. Because that list reproduces what `docs/operations.md` currently asks a human to do, any change to it is a change to the provisioning contract and has to be released like one.
- The hosting substrate is chosen by measured unit cost of one organisation instance per month at a reference workload, not by preference or familiarity. Inference topology dominates that number and therefore has to be priced as part of the same measurement rather than settled separately.
- Hosting region stops being a configuration detail and becomes a contractual commitment. An instance provisioned in a stated region cannot quietly move, and the control plane has to be able to place an instance by region at creation time rather than treat placement as a deployment default.
- Operating instances on a customer's behalf creates data-processor obligations that are product work, not paperwork done later: a data processing agreement, a maintained sub-processor list covering the hosting substrate and any external model service, and a stated region per instance. The obligations attach to the hosted path only; a self-hosted partner keeps them entirely.
- Fleet telemetry is operational by default and never content. Health, version, resource use, error rates, and job outcomes flow to the control plane. Anything richer is opt-in per instance, time-boxed, and expires on its own rather than on someone remembering to turn it off. No vault content, no query text, no **Node** or **Central** documents, and no per-member identifiers leave an instance as telemetry.
- Citadel gains no new configuration for any of the above, which is the point rather than an omission. Forbidden by this decision: a setting naming another instance, a credential valid at more than one instance, a registry or directory the application can query, and any code path whose behaviour depends on how many instances exist. A value that must differ per organisation belongs to the provisioner's contract, and a feature that needs cross-instance knowledge belongs to the control plane or does not get built.
