# Evidence Is Retained And Attested At Capture, Not Recomputed At Read

Citadel already keeps the text behind much of what it indexes: `RepoContentFile.content` (`kb/repo_content_sync.py:64`) and the Obsidian sync's `SourceRevision.body` (`kb/obsidian_sync.py:65`) both copy full source text at sync time, so retention is not the missing piece. Fingerprinting that copy at the moment it is captured is. `Citadel.ingest` computes `sha256(data.encode("utf-8"))` (`kb/service.py:86`) and spends it immediately as half of an in-process duplicate key, `(dataset, content_hash)`; the value is never stored with the record and never reaches a reader. The connectors compute their own hashes for their own purposes, `RepoContentFile.content_hash` (`kb/repo_content_sync.py:73`) for change detection and `content_hash()` in `kb/obsidian_sync.py:24` for revision comparison, each private to one sync path. What a reader actually receives is computed at read time: `result_content_sha256` (`kb/server.py:2602`) hashes the result dict as it is about to be serialised and `with_result_metadata` (`kb/server.py:2648`) attaches it as `_citadel.content_sha256`. That function has exactly one production caller, the `POST /search` handler at `kb/server.py:6506`, so the digest rides the search envelope and no other response shape; `GET /api/documents/{document_id}` (`kb/server.py:5327`) returns the resolved document with no envelope around it. Adding the same read-time computation to the second route would even the coverage out while leaving the number saying what it says today, which is that this response was assembled from what the store held at the time of the call. An audit asks a different question. So the **Organization Vault** retains the durable evidence behind a cited claim, fingerprints it at capture, stores that attested fingerprint with the record, and returns it on every retrieval path; the read-time digest keeps its place as a transit-integrity check and is described as one wherever it appears. `CONTEXT.md` has carried the shape of this since the 2026-07-15 grill and has been explicit that half of it was postponed:

> Two forms: the **v1 minimal form** is a stable source pointer (connector id + URL + checked-at, e.g. a GitHub digest id, a **Node** capture id, a Linear issue) that already exists on the ingest paths; the **target full form** additionally retains the source evidence for reprocessing (a later plan).

Retained-evidence **Source Snapshot**, the full form, stops being a later plan. The mechanism is deliberately small. Every retained document gets a SHA-256 over its stored bytes at capture. Each fingerprint is linked into a chain as `hash(previous_chain_hash + document_hash)`, so ordering is covered rather than only membership, and the chain head is signed on a schedule with a key Citadel controls, which gives the sequence an author instead of leaving it recomputable by anyone. The records use the W3C PROV triple as vocabulary: the entity is the retained copy and its fingerprint, the activity is the capture run that produced it (connector, dataset, time), and the agent is whoever ran it, a sync process or a **Seat** capture or a **Vault Member** acting directly. PROV names the three record types before anything is written, which is cheaper than renaming them after the first partner integration is built against them.

**Considered Options**

- **Read-time digest only (status quo):** already written, costs nothing further. It hashes the result minus its own envelope, so two responses carrying the same payload agree, and a reader can tell that a response was not mangled in transit. It cannot speak to whether the stored evidence matches what the connector fetched, because its input is whatever the store returns at the moment of the call. Widening it to the drill-down route would spread the coverage without changing the meaning.
- **Capture-time attested fingerprint plus a signed chain (chosen):** a figure resolves to a document, to the retained copy, to a value the node committed to before anyone asked for it, and reordering is detectable rather than only substitution. The cost is real: a signing key to hold, rotate, and protect; a chain write on every capture path; verification tooling that has to exist for the attestation to be worth anything to a third party; and retention becoming something the vault owes rather than something it offers.
- **Self-hosted transparency log:** a Merkle log with inclusion proofs, under our own operation. Rejected on cost against benefit. It needs a log server, a backing database, and a signer standing per instance, and a fleet of single-organisation instances multiplies that by the fleet. What it proves is what the signed chain already proves, because both are attested by the same operator.
- **Public transparency log:** submitting the signed chain head to a public log on a schedule is one outbound call, and it is the only option here that survives an operator who rewrites history. It adds an external dependency and puts a hash (not content) outside the node. This is queued behind the chain rather than rejected: there has to be a chain head before there is anything to submit.
- **On-chain anchoring:** buys the same immutability property as a public log. It brings a chain client, key custody, fees, and network availability onto the path a compliance report depends on. Rejected for that reason. Blockchain-backed agent identity is a separate question and is being looked at on its own terms.

**Consequences**

- Retention is now an obligation as well as a feature. An erasure request has to reach retained copies, so the erasure workflow either propagates into the evidence store or records a legal-hold justification for what it leaves behind. Removal has to keep the chain verifiable, which means it is recorded as a new entry rather than performed by editing an old one.
- The evidence store is append-only by construction, and the **Learning Process** is forbidden from touching it. Evolve keeps revising **Structured Knowledge** and rebuilding derived structure. An auditor's trace is therefore immune to a pass that runs after the report was produced.
- **Knowledge Index** and **Knowledge Mesh** remain rebuildable projections, per [ADR-0010](0010-structured-knowledge-durable-source-of-truth.md). Retained evidence is the one layer that cannot be rebuilt from anything else, which is precisely why it is the layer worth signing.
- [ADR-0001](0001-github-vault-backup-mirror.md) is superseded and folds in here. A manifest in a mirror repository is weaker than a retained attested copy, and running both leaves two answers to the question of where the durable copy lives. The obligation ADR-0001 was carrying transfers rather than disappearing: [ADR-0016](0016-ingested-documents-are-byte-stable.md) records that duplicate documents could not be cleaned up safely while prior versions were unrecoverable, and it is the evidence store that has to make them recoverable now.
- Retrieval paths return the attested value, which is a change to more than one route. The search envelope, `GET /api/documents/{document_id}`, and every surface that cites a document (MCP tools, CLI, the dashboard) each read it. The transit digest and the attested fingerprint are separate fields with separate names, and each name says which of the two it is, following [ADR-0019](0019-activity-counters-are-named-by-their-scope.md): a field whose meaning depends on the route it arrived through is a field readers will misread.
- A capture-time fingerprint is a record the server wrote, so it is attestable in the sense [ADR-0012](0012-attested-trust-vs-content-hint.md) requires, unlike anything derived from body text. It attests which bytes were captured and when. It makes no claim that the content is correct, and `content_hint` keeps its own separate job.
- Byte stability is a precondition, so [ADR-0016](0016-ingested-documents-are-byte-stable.md) becomes load-bearing rather than tidy. A fingerprint over a body carrying a wall-clock line changes on every sync of an unchanged file and attests nothing. The structural header [ADR-0017](0017-structural-provenance-outranks-inherited-trust.md) relies on is what a PROV entity binds to when the source is a governed sync.
- The honest limit, stated where it will be read: a signed chain proves that no external party altered or reordered the evidence. It does not prove that the operator did not rewrite the chain and re-sign it, because the operator holds the key. Closing that threat model takes one outbound call, submitting the chain head to a public transparency log, which is why the self-hosted log lost and why on-chain anchoring, which buys the same property with a dependency on the compliance-critical path, lost too.
